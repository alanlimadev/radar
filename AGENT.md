# AGENT.md — RADAR Project Guidelines

This file provides authoritative architectural context, domain invariants, workflows, and conventions for AI agents working in this repository.

---

## 1. Project Overview

**RADAR** is a modular NestJS framework for building low-latency, real-time multiplayer applications and games designed to run over local wireless networks (WLAN) **without internet connectivity**.

- **Primary Repository Role:** Backend framework engine (`src/core`) + Quiz PoC implementation (`src/quiz`).
- **Partner Project:** [`offline-game-quiz`](../offline-game-quiz) — React + Vite frontend acting as the Kahoot-style offline proof-of-concept.
- **Runtime Port:** `3333` (Hosts both REST API and Socket.IO WebSocket gateway).
- **Swagger Documentation:** `http://localhost:3333/swagger`.

## 2. Architecture & Directory Layout

The codebase has undergone a significant refactor from a monolithic Kahoot backend to an extensible framework:

```
src/

├── main.ts                    # Application bootstrap, Swagger setup, CORS, ValidationPipe
│

│   ├── controllers/           # RoomController (REST endpoints under /rooms) & DTOs
│   ├── gateways/              # RadarGateway (Socket.IO) & RadarWsExceptionFilter
│   ├── interfaces/            # IGameDefinition, Room, Player, GameAction, ActionResult
│   ├── network/               # pin.util.ts (6-digit PIN generator)
│   ├── services/              # RoomManagerService (in-memory state + DB sync) & GameRegistryService
│   └── radar.module.ts        # Exported global core module
│
├── quiz/                      # 🎮 QUIZ POC MODULE (GAME DEFINITION)
│   ├── quiz.controller.ts     # REST endpoints for Quiz/Question/Alternative CRUD (/quizzes)
│   ├── quiz.service.ts        # Quiz business logic and database queries
│   ├── quiz.repository.ts     # Data access layer using PrismaClient
│   ├── quiz-game.definition.ts# Implements IGameDefinition for the Kahoot-style quiz
│   └── quiz.module.ts         # Registers QuizGameDefinition into GameRegistryService on init
│
├── auth/                      # 🔐 Authentication module (JWT, bcrypt, Passport)
├── user/                      # 👤 User/Host profiles
└── prisma/                    # 🗄️ Shared PrismaService and database migrations
```

> ⚠️ **CRITICAL ARCHITECTURAL BOUNDARY:**
> - **`src/core` MUST NEVER** import or contain domain logic from `src/quiz` or any specific game. The core engine is 100% game-agnostic.
> - **`src/game-session/` is completely DEPRECATED and REMOVED.** Do not reference or reintroduce files under `src/game-session/`.
> - All new games must implement `IGameDefinition` and register into `GameRegistryService`.

## 3. Core Concepts & Domain Invariants

### 3.1 Rooms and PINs
- Each room is identified by a unique **6-digit numerical PIN** generated by `pin.util.ts` (`generateRoomPin()`).
- Rooms transition through states: `LOBBY` ➔ `IN_PROGRESS` ➔ `FINISHED`.
- Rooms are kept in-memory inside `RoomManagerService` for sub-millisecond game loop execution and synchronized with the PostgreSQL `game_rooms` and `room_players` tables.

### 3.2 Roles & Sockets
- **Host:** Creates the room (`POST /rooms`) and joins the WebSocket via `radar:joinAsHost` (or legacy `joinAsHost`). The host is **never** added to the `players` map or final player leaderboard.
- **Player:** Joins via `radar:joinRoom` (or legacy `joinSession`). Gets assigned a unique `playerId` (UUID).
- **Reconnection:** If a socket disconnects, the player is flagged `connected: false`. If a client reconnects with the same `playerName` to that `roomCode`, their session is restored and state re-synced.
- **Anti-Cheat State Segregation:** `IGameDefinition.getClientState(state, forPlayer, isHost)` filters out sensitive state:
  - Players **never** receive `isCorrect: true` on alternatives while questions are active.
  - Hosts receive full management state including question timers and answer tallies.

### 3.3 Quiz Business Rules
- Each question must contain **exactly 4 alternatives**.
- Exactly **1 alternative** must be flagged `isCorrect: true`.
- Quizzes are owned by the `Host` (`createdBy` matches `req.user.id`).
- Quizzes with existing sessions cannot be deleted without handling foreign key constraints (handled with cascade or 409 Conflict).

## 4. WebSocket Event Contracts

The `RadarGateway` exposes two concurrent protocols on the same gateway:

### 4.1 Universal RADAR Protocol (`radar:*`)
Used by modern clients and any future game implementations:

| Event Name | Direction | Payload |
|---|---|---|
| `radar:joinAsHost` | Client ➔ Server | `{ roomCode: string }` |
| `radar:joinRoom` | Client ➔ Server | `{ roomCode: string, playerName: string, metadata?: any }` |
| `radar:dispatchAction`| Client ➔ Server | `{ type: string, payload?: any, roomCode?: string }` |
| `radar:leaveRoom` | Client ➔ Server | _(none)_ |
| `radar:roomJoined` | Server ➔ Client | `{ isHost, room, state, players, isReconnection }` |
| `radar:playerJoined` | Server ➔ Client | `{ player, totalPlayers }` (Broadcast to peers) |
| `radar:playerLeft` | Server ➔ Client | `{ playerId, playerName }` |
| `radar:stateUpdated` | Server ➔ Client | `{ state, status }` (Filtered per recipient) |
| `radar:customEvent` | Server ➔ Client | `{ event: string, payload: any }` |
| `radar:gameEnded` | Server ➔ Client | `{ results: any }` |
| `radar:error` | Server ➔ Client | `{ message: string }` |

### 4.2 Legacy Protocol (Kahoot PoC Compatibility)
Maintained for backward compatibility with `offline-game-quiz`:

| Event Name | Role | Payload | Response / Broadcast |
|---|---|---|---|
| `joinAsHost` | Host | `{ sessionId: string \| number }` | Emits `existingPlayers` to host |
| `joinSession` | Player | `{ sessionId, playerName }` | Emits `existingPlayers` to joiner; `playerJoined` to peers |
| `startQuiz` | Host | _(none)_ | Dispatches `START_GAME`; emits `quizStarted` |
| `nextQuestion` | Host | _(none)_ | Dispatches `NEXT_QUESTION`; emits `nextQuestion` or `quizEnded` |
| `submitAnswer` | Player | `{ questionId, alternativeId }` | Dispatches `SUBMIT_ANSWER`; emits `answerSubmitted` |
| `getScores` | Any | _(none)_ | Emits `scoresUpdate` with leaderboard |

## 5. Development & Testing Commands

Always run commands from the `radar-tcc` root directory:

```bash
# Development
npm run start:dev        # Start NestJS with hot-reload
npm run build            # Compile TypeScript build

# Testing
npm test                 # Run Jest unit tests (must pass before pushing)
npm run test:cov         # Generate code coverage report
npm test -- path/to/spec.ts # Run a specific test suite

# Code Quality
npm run lint             # ESLint with auto-fix
npm run format           # Prettier formatting

# Prisma ORM & Database
npx prisma migrate dev --name <migration_name> # Generate and apply DB migration
npx prisma generate                            # Regenerate Prisma Client
npx prisma studio                              # Web UI for database inspection

# Docker
docker compose up --build -d # Launch Postgres + API containers
docker compose logs -f       # Stream container logs
docker compose down          # Stop all containers

# Desktop Application Build (Standalone .exe)
# Always refer to docs/BUILD_EXECUTABLE.md for complete details
npm run build:app            # Run from radar-tcc to compile all and build RADAR-Quiz_1.0.0_x64-setup.exe
# Or: .\build-app.ps1 from workspace root
```

## 6. Commit Convention

**Strict Conventional Commits in English.**

> ⛔ **ABSOLUTE RULE: NO EMOJIS IN COMMIT MESSAGES OR PR TITLES.**

- **Pattern:** `<type>(<scope>): <imperative description>`
- **Valid Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`, `ci`
- **Examples:**
  - `feat(core): implement player timeout handling in room manager`
  - `fix(quiz): ensure accurate score calculation on late submissions`
  - `docs(api): update room controller swagger annotations`
  - `test(core): add edge-case tests for pin collision resolution`

## 7. Desktop Executable Build Workflow

When tasked with generating, packaging, or modifying the standalone desktop installer (`.exe`):

1. **Mandatory Documentation:** Always read and follow [`docs/BUILD_EXECUTABLE.md`](./docs/BUILD_EXECUTABLE.md). It contains the complete architectural specification, Tauri sidecar configuration, SQLite AppData paths, and diagnostic steps.
2. **Build Execution:** Never build partial steps manually unless debugging. Use the root automation script `.\build-app.ps1`.
3. **Database & Persistence:** The standalone runtime uses SQLite (`radar.db`) in the per-user app data dir (`%APPDATA%\com.radar.quiz\data\radar.db` on Windows, `~/.local/share/com.radar.quiz/data/radar.db` on Linux). The template DB shipped in the bundle is copied only when the user DB does not exist. On startup, `PrismaService` validates the expected tables/columns via `REQUIRED_SCHEMA`; if the DB is incompatible (from an older version or corrupt) it is backed up as `radar.db.bak-<timestamp>` and recreated from the template, avoiding `500 Internal server error` (Prisma `P2021`/`P2022`). When changing `prisma/schema.prisma`, update `REQUIRED_SCHEMA` in `src/prisma/prisma.service.ts`. Do not hardcode database paths to relative directories.
4. **Network & Hotspot:** The backend exposes `GET /rooms/network-ip` to auto-detect the host IP, prioritizing the Windows Mobile Hotspot adapter (`192.168.137.1`).
5. **Linux Builds (`.deb` / `.AppImage`):** Tauri does not cross-compile from Windows to Linux. To produce Linux bundles, use the Docker environment in `scripts/linux-docker/` via `npm run build:app:linux:docker` (Windows) or `npm run build:app:linux:docker:sh` (Linux/macOS). Docker Desktop must be running. On a native Linux machine with Tauri system deps, `npm run build:app:linux` (`scripts/build-app.sh`) works directly. See [`docs/BUILD_EXECUTABLE.md`](./docs/BUILD_EXECUTABLE.md).
